# Phase 6.5: Draft-Sichtung + Promotion — Research

**Researched:** 2026-05-12
**Domain:** Offline-first React-Native screen + draft → plan_element promotion (DB-shape mapping, sync, i18n, atomic writes)
**Confidence:** HIGH

## Summary

Phase 6.5 schließt eine klar abgrenzbare Lücke im Code: Phase 6 schreibt `bed_drafts`/`plant_drafts`/`observation_drafts`, aber niemand macht daraus `plan_elements`. Der Home-Screen rendert ausschließlich `plan_elements` (siehe `app/app/(app)/index.tsx:74`), darum sieht der Nutzer "Noch kein Gartenplan" trotz erfolgreichem Import.

Die gesamte Infrastruktur, die wir brauchen, existiert bereits:
- Storage-Adapter mit Multi-Store-Atomic-Writes (`writeWithOutbox`, `IndexedDbAdapter:264`)
- SyncWorker-Push für `plan_elements` UND alle Draft-Tabellen (Commit 9372cad + `SyncWorker.ts:236-242`)
- `loadPendingDrafts()` Repo-Funktion ist schon implementiert (`importRepo.ts:288`)
- Skia/SVG-Renderer für Elemente steht (`GardenPlanView.tsx`)
- i18n-Pattern (`packages/shared/src/i18n/de.json`)

Was **fehlt**: ein Sichtungs-Screen, eine `promoteDraft()`-Funktion, ein Schema-Feld für `provenance.importedFrom` auf `plan_elements` (M07-Spec verlangt es, aber Migration 014 hat nur `ai_result_id`), und eine geometrische Default-Belegung (xM/yM/widthM/heightM) für Beete, deren Source-Draft nur cm-Dimensionen kennt.

**Primary recommendation:** Eine neue Migration 017 fügt `imported_from` (UUID FK auf `import_items`) und `provenance` (jsonb) zu `plan_elements` hinzu, ein neuer Screen `app/app/(app)/import/review.tsx` rendert per Sektion (Beete/Pflanzen/Beobachtungen) Cards mit Annehmen/Verwerfen/Editieren-Buttons, und `promoteDraft()` in `app/src/lib/draftPromotionRepo.ts` macht die atomare Doppel-Write (Draft → status='promoted' + plan_element insert) via existierendem `writeWithOutbox`-Pattern. Beobachtungen werden NICHT zu `plan_elements` (sie sind keine räumlichen Elemente) — sie bleiben Drafts mit `status='promoted'` als reine Annotation.

### Pattern 1: Atomic Multi-Write via writeWithOutbox

**What:** `writeWithOutbox` ist bereits als Multi-Store-Transaction implementiert (`IndexedDbAdapter:264`). Pro Promote-Operation müssen wir aber ZWEI separate Writes machen (plan_element insert + draft update). Diese sind NICHT atomar zueinander — siehe Pitfall 1.

**When to use:** Jede Operation, die eine Row schreibt + ein Outbox-Entry für späteren Server-Push erzeugt.

**Example:** [VERIFIED: existing pattern, `gardenPlanRepo.ts:62-69`]
```typescript
await storage.writeWithOutbox('plan_elements', newElement, {
  entity: 'plan_elements',
  rowId: newElement.id,
  operation: 'insert',
  payload: newElement as unknown as Record<string, unknown>,
});
```

### Pattern 2: Status-Update auf Draft-Row (LWW)

**What:** Drafts haben `status` ('pending'|'promoted'|'dismissed'), `promotedAt` und `deletedAt`. Status-Update ist ein normaler `update`-Outbox-Entry. Der Server hat den `zz_set_updated_at`-Trigger (Migration 016), aber KEIN `aa_lww_guard` (Drafts sind logisch single-writer).

**When to use:** Nach Promote: Draft auf `status='promoted'` + `promotedAt` setzen. Nach Verwerfen: Draft auf `deletedAt=now` (nicht status='dismissed' nur — siehe Success Criterion 4).

**Example:** [VERIFIED: existing import_items mapper handles this, `rowMappers.ts:441-490`]
```typescript
const promotedDraft: BedDraftRow = {
  ...existing,
  status: 'promoted',
  promotedAt: new Date().toISOString(),
  updatedAt: new Date().toISOString(),
  updatedByUserId: userId,
};
await storage.writeWithOutbox('bed_drafts', promotedDraft, {
  entity: 'bed_drafts',
  rowId: promotedDraft.id,
  operation: 'update',
  payload: promotedDraft as unknown as Record<string, unknown>,
});
```

### Pattern 3: Mode-Guard (assertAccount)

**What:** Alle Write-Repos werfen, wenn `mode !== 'account'`. [VERIFIED: `importRepo.ts:23`, `gardenPlanRepo.ts:14`]

**When to use:** Am Anfang jeder neuen `promoteDraft`/`dismissDraft`-Funktion.

```typescript
function assertAccount(mode: AuthMode): void {
  if (mode !== 'account') throw new Error('drafts are account-only');
}
```

### Anti-Patterns to Avoid
- **Navigation-Params für Draft-Daten:** Phase 6 lernte das harte Weg (Pitfall 1 in `06-RESEARCH.md` — daher `importStore`). Für 6.5 GLEICH: Draft-IDs aus dem Repo lesen, nicht via params durchreichen.
- **Direkte Supabase-Aufrufe im Screen:** Immer über Repo-Layer + `writeWithOutbox`. Nie `supabase.from(...).insert(...)` aus dem Screen — bricht Offline-First.
- **Synchronous loop für Bulk-Auto-Promote ohne yield:** Bei N=200 Drafts blockiert das den Main-Thread. Stattdessen sequenziell mit `await` (gibt Event-Loop frei) und progressivem Toast.
- **Geometrie-Felder NULLable lassen:** `plan_elements.x_m/y_m/width_m/height_m` sind NOT NULL in Migration 014 — beim Promote müssen wir Defaults berechnen, sonst wirft Postgres.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomares Persist+Outbox | Eigenes try/rollback | `storage.writeWithOutbox()` | Bereits per IDBP-Transaction atomar (`IndexedDbAdapter:264`) |
| Camel↔Snake Mapping für plan_elements | Manuelle Field-Lists | `planElementToDb()` (`rowMappers.ts:409`) | Existiert; bei Schema-Erweiterung um 1 Feld erweitern |
| Camel↔Snake Mapping für Drafts | Per-entity mapper | `importEntityToDb()` (`rowMappers.ts:441`) | Generic mapper, fügt nur den neuen Feldnamen zur Map hinzu |
| Sync-Push debouncing | setTimeout-Logic | `scheduleWriteDebounced()` (`SyncTriggers.ts:18`) | Bereits 500ms-Debounce |
| LWW-Conflict-Handling | Manuelle Timestamp-Compare | Postgres-Trigger `aa_lww_guard` | Bereits server-side aktiv für plan_elements |
| Outbox-Push-Routing | Eigener Switch | `dispatchPush()` (`SyncWorker.ts:228`) | Cases für plan_elements + Draft-Tables existieren bereits |
| UUID-Erzeugung | uuid-Lib | `randomId()` Helper (`importRepo.ts:27`) | Bereits Pattern: `crypto.randomUUID()` mit Fallback |
| Confidence-Mapping (number → 'high'/'medium'/'low') | Inline-If | Reuse `confidenceToState()` (`ImportEntityCard.tsx:11`) | Bereits 3-stufig in der App definiert |

**Key insight:** Die gesamte Outbox/Sync/Mapper-Infrastruktur ist Phase-3-/-4-/-6-Erbe und voll einsatzbereit. Die einzige Schema-Erweiterung ist 2 Felder auf `plan_elements`. Alles andere ist neue UI + ein Repo-Modul + i18n-Keys.

## Common Pitfalls

### Pitfall 1: Promotion ist NICHT atomar zwischen plan_element-Insert und Draft-Status-Update

**What goes wrong:** `promoteDraft` macht zwei separate `writeWithOutbox`-Aufrufe. Wenn der zweite fehlschlägt (z.B. IndexedDB quota exceeded), entsteht ein Geist-Plan-Element ohne korrespondierenden 'promoted' Draft-Status. Beim nächsten Sichtungs-Aufruf taucht der Draft wieder als 'pending' auf, und der User klickt "Annehmen" erneut → Duplikat im Plan.

**Why it happens:** `writeWithOutbox` ist atomar PRO Aufruf (Row + Outbox-Entry in einer IDBP-Transaction), aber NICHT zwischen mehreren Aufrufen.

**How to avoid:** Drei Optionen, in Reihenfolge der Komplexität:
1. **Detection first (recommended for MVP):** Bei `promoteDraft` zuerst prüfen ob Draft bereits einen `plan_element` mit `provenance.importedFrom = importItemId` hat → Idempotent skip.
2. **Single multi-store transaction:** `writeWithOutbox` um Multi-Row-Variante erweitern (`writeManyWithOutbox`). Größerer Refactor — vermeiden für MVP.
3. **Forward-only promotion:** Wenn plan_element-Insert klappt, Draft-Update als Best-Effort (Catch + Log). Bei Re-Sichtung: Promotion-Status aus plan_elements ableiten, nicht aus Draft.status. Konsistent mit "Source of Truth"-Prinzip.

**Warning signs:** Doppelte plan_elements mit gleicher `importedFrom`-ID nach Sync-Recovery. Test schreiben: simulate write-failure auf zweiten Aufruf → erwarten `promoteDraft` wirft + plan_element wird NICHT inserted (oder Draft wird via Re-Lookup übersprungen).

### Pitfall 2: Default-Geometrie für promoted Beete

**What goes wrong:** `bed_drafts` haben nur `lengthCm` + `widthCm` (Maße in cm), aber `plan_elements` braucht `xM, yM, widthM, heightM` (Position UND Größe in Meter). Ohne Default-Layout landen alle Beete bei (0,0) und überlappen visuell.

**Why it happens:** Die Import-Bridge transportiert keine Geometrie aus Claude.ai (das Bild ist nicht maßstabsgerecht). Ein Beet ist "ca. 2×3 m groß" — wo es im Garten liegt, weiß nur Dirk.

**How to avoid:** Im Repo eine Layout-Funktion: `nextFreeBedSlot(existingElements, dimensions, newSize)` macht Reihen-Stacking ab (1m, 1m) mit 50cm Abständen. Ergibt deterministisches, nicht-überlappendes Layout. Wenn `lengthCm`/`widthCm` NULL sind: Default 1.5m × 1m. Phase 7 ersetzt durch Drag&Drop. **Garden-Größe ist nötig** — `loadDimensions(gardenId)` liefert sie (`gardenPlanRepo.ts:78`).

**Warning signs:** Mehrere promoted Beete an gleicher Position; Beete außerhalb der Garten-Grenzen.

### Pitfall 3: Beobachtungen sind keine räumlichen Elemente

**What goes wrong:** Versuch, `observation_drafts` zu `plan_elements` zu promoten. Aber Beobachtungen ("Schnecken im Hochbeet") haben keine Geometrie und passen nicht in das `plan_elements`-Schema (NOT NULL auf x/y/width/height).

**How to avoid:** Beobachtungen werden NICHT zu `plan_elements`. Sie bleiben als `observation_drafts` mit `status='promoted'` als reine Annotation. UI: in Sektion "Beobachtungen" ist "Annehmen" = "Als gelesen markieren" (Status auf 'promoted', kein plan_element-Insert). "Verwerfen" funktioniert wie bei anderen.

**Warning signs:** Schema-Errors beim Promote von Observations. Empty Plan trotz "promoted" Observations.

### Pitfall 4: Pflanzen brauchen Bezug zu einem promoted Bed

**What goes wrong:** `plant_drafts.bedDraftId` ist NULLable und in der Phase-6-Implementierung immer `null` (`importRepo.ts:173` — Kommentar: "linkage handled in Phase 6-03 (promotion flow)"). Ohne Bezug landen promoted Pflanzen ohne räumlichen Kontext im Plan.

**How to avoid:** Promotion-Reihenfolge: zuerst alle ausgewählten Beete promoten, dann Pflanzen. Bei Pflanze: Lookup `bedRefLocalId` (aus `import_items.payload.bedRef`) → finde promoted bed_draft → lese dessen `plan_element`-ID → schreibe als `provenance.parentBedId`. UI: bei Edit-Form für Pflanze ein Dropdown "Beet" mit allen verfügbaren Beeten (promoted + pending).

**Warning signs:** Pflanzen ohne sichtbares Beet im Plan. `plan_elements` mit `elementType='Pflanze'` aber ohne sinnvollen `xM/yM`.

### Pitfall 5: Auto-Promote-Schwellwert reagiert nicht auf Toggle-Wechsel

**What goes wrong:** User aktiviert Auto-Promote, Drafts werden batch-promoted. Dann deaktiviert er den Toggle — bereits promoted Drafts bleiben promoted (richtig), aber wenn er den Toggle erneut aktiviert mit einem niedrigeren Schwellwert, was passiert mit den schon-pending Drafts mit confidence 0.7?

**How to avoid:** Toggle-Effekt klar definieren: "Wenn aktiviert, werden alle PENDING Drafts mit confidence ≥ Schwellwert sofort promoted." Re-Aktivierung mit niedrigerem Schwellwert promotet die zusätzlichen. Schwellwert per Slider oder fester Wert (0.8 per Spec). Im Toggle-onChange: `if (enabled) promoteAllAboveThreshold(threshold)`.

**Warning signs:** Inkonsistenter UI-State; User klickt Toggle und nichts passiert sichtbar.

### Pitfall 6: writeWithOutbox sequentiell in for-loop (200 Drafts)

**What goes wrong:** Auto-Promote bei vollem Import (z.B. 50 Beete + 100 Pflanzen + 50 Beobachtungen) macht 200+ sequenzielle `writeWithOutbox`-Aufrufe. Jeder ist eine eigene IDBP-Transaktion → langsam, blockierender Main-Thread.

**Why it happens:** Pattern aus `saveImport` (`importRepo.ts:88-268`) ist sequenziell. Für Phase-6-Save war das ok (1× pro Import), aber Promotion-Loop ist häufiger.

**How to avoid:** Pro Promote 2 Aufrufe (plan_element + draft-update). Akzeptabel bis ~50 Items. Bei mehr: Progress-Indicator + visuelles Feedback (`Promotiere {n} von {total}...`). Kein vorzeitiger Optimierungsdruck — MVP-Ziel ist 200 Drafts max (Performance-Hinweis im Phase-Brief).

**Warning signs:** UI freezes bei großen Imports; "Page unresponsive" Warnungen im Browser.

```sql
-- Pattern: Migration 014 — Sektionen, RLS bleibt unverändert, Invariant-Block

-- Section 1: Add provenance columns to plan_elements
ALTER TABLE public.plan_elements
  ADD COLUMN IF NOT EXISTS imported_from uuid REFERENCES public.import_items(id) ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS provenance    jsonb;

CREATE INDEX IF NOT EXISTS idx_plan_elements_imported_from
  ON public.plan_elements (imported_from) WHERE imported_from IS NOT NULL AND deleted_at IS NULL;

-- Section 2: Drop legacy ai_result_id column (was orphaned by migration 015 CASCADE drop of ai_results)
-- The column may already be gone if Postgres removed it via the CASCADE; ALTER ... DROP IF EXISTS is safe.
ALTER TABLE public.plan_elements DROP COLUMN IF EXISTS ai_result_id;

-- Section 3: Invariants
DO $$ DECLARE cnt int;
BEGIN
  SELECT count(*) INTO cnt FROM information_schema.columns
    WHERE table_schema = 'public' AND table_name = 'plan_elements'
      AND column_name IN ('imported_from', 'provenance');
  IF cnt <> 2 THEN
    RAISE EXCEPTION 'migration_017_invariant: expected 2 new cols on plan_elements, got %', cnt;
  END IF;

  SELECT count(*) INTO cnt FROM information_schema.columns
    WHERE table_schema = 'public' AND table_name = 'plan_elements' AND column_name = 'ai_result_id';
  IF cnt <> 0 THEN
    RAISE EXCEPTION 'migration_017_invariant: ai_result_id should be dropped';
  END IF;

  RAISE NOTICE 'migration_017 ok: plan_elements.imported_from + provenance added';
END $$;
```

### Example 2: promoteDraft repo function

```typescript
// Source: New file app/src/lib/draftPromotionRepo.ts
// Pattern: gardenPlanRepo.ts (assertAccount + writeWithOutbox + scheduleWriteDebounced)

import { storage } from '../storage';
import { useAuthStore, type AuthMode } from '../stores/authStore';
import type {
  BedDraftRow, PlantDraftRow, ObservationDraftRow,
  PlanElementRow, GardenDimensionsRow,
} from '@spatenstich/shared';
import { OutboxEnqueueError } from './errors';
import { scheduleWriteDebounced } from './sync/SyncTriggers';

function assertAccount(mode: AuthMode): void {
  if (mode !== 'account') throw new Error('drafts are account-only');
}

function randomId(): string {
  if (typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function') {
    return crypto.randomUUID();
  }
  return `${Date.now()}-${Math.random().toString(36).slice(2, 10)}`;
}

/** Naive grid layout: stack new beds in rows starting at (1m, 1m), 50cm gap. */
function nextFreeBedSlot(
  existing: PlanElementRow[],
  dims: GardenDimensionsRow,
  size: { widthM: number; heightM: number },
): { xM: number; yM: number } {
  const GAP = 0.5;
  const beds = existing.filter((e) => e.elementType === 'Beet');
  let cursorX = 1, cursorY = 1, rowMaxH = 0;
  for (const _ of beds) {
    cursorX += size.widthM + GAP;
    if (cursorX + size.widthM > dims.widthM - 1) {
      cursorX = 1;
      cursorY += rowMaxH + GAP;
      rowMaxH = 0;
    }
    rowMaxH = Math.max(rowMaxH, size.heightM);
  }
  return { xM: cursorX, yM: cursorY };
}

export async function promoteBedDraft(
  mode: AuthMode,
  draft: BedDraftRow,
  dims: GardenDimensionsRow,
  existingElements: PlanElementRow[],
  importItemId: string,
): Promise<PlanElementRow> {
  assertAccount(mode);
  const userId = useAuthStore.getState().userId;
  if (!userId) throw new Error('not_authenticated');

  // Idempotency check (Pitfall 1): is this draft already promoted?
  const dup = existingElements.find(
    (e) => (e as any).importedFrom === importItemId && e.deletedAt === null,
  );
  if (dup) return dup;

  const widthM = (draft.lengthCm ?? 150) / 100;
  const heightM = (draft.widthCm ?? 100) / 100;
  const { xM, yM } = nextFreeBedSlot(existingElements, dims, { widthM, heightM });
  const now = new Date().toISOString();

  const element: PlanElementRow & { importedFrom?: string; provenance?: Record<string, unknown> } = {
    id: randomId(),
    gardenId: draft.gardenId,
    elementType: 'Beet',
    label: draft.label,
    xM, yM, widthM, heightM,
    confidence: draft.confidence !== null && draft.confidence >= 0.8 ? 'high'
              : draft.confidence !== null && draft.confidence >= 0.6 ? 'medium' : 'low',
    isAccepted: true,
    createdAt: now,
    updatedAt: now,
    updatedByUserId: userId,
    deletedAt: null,
    importedFrom: importItemId,
    provenance: { source: 'claude-ai-project', sunExposure: draft.sunExposure, soilNotes: draft.soilNotes },
  };

  // Write 1: insert plan_element
  try {
    await storage.writeWithOutbox('plan_elements', element, {
      entity: 'plan_elements',
      rowId: element.id,
      operation: 'insert',
      payload: element as unknown as Record<string, unknown>,
    });
  } catch (cause) {
    throw new OutboxEnqueueError('plan_elements', element.id, cause);
  }

  // Write 2: update draft status
  const promotedDraft: BedDraftRow = {
    ...draft,
    status: 'promoted',
    promotedAt: now,
    updatedAt: now,
    updatedByUserId: userId,
  };
  try {
    await storage.writeWithOutbox('bed_drafts', promotedDraft, {
      entity: 'bed_drafts',
      rowId: draft.id,
      operation: 'update',
      payload: promotedDraft as unknown as Record<string, unknown>,
    });
  } catch (cause) {
    throw new OutboxEnqueueError('bed_drafts', draft.id, cause);
  }

  scheduleWriteDebounced();
  return element;
}

export async function dismissDraft(
  mode: AuthMode,
  entity: 'bed_drafts' | 'plant_drafts' | 'observation_drafts',
  draft: BedDraftRow | PlantDraftRow | ObservationDraftRow,
): Promise<void> {
  assertAccount(mode);
  const userId = useAuthStore.getState().userId;
  if (!userId) throw new Error('not_authenticated');
  const now = new Date().toISOString();
  const updated = { ...draft, deletedAt: now, updatedAt: now, updatedByUserId: userId };
  try {
    await storage.writeWithOutbox(entity, updated as any, {
      entity,
      rowId: draft.id,
      operation: 'update',
      payload: updated as unknown as Record<string, unknown>,
    });
  } catch (cause) {
    throw new OutboxEnqueueError(entity, draft.id, cause);
  }
  scheduleWriteDebounced();
}
```
