# Phase 09.1: Editor-Element-Bearbeitung - Research

**Researched:** 2026-05-29
**Domain:** Cross-platform Plan-Editor (Web SVG + iPhone Skia) — Element-Bearbeitung nach dem Platzieren via Trigger-Geste + Modal + Drag-Handles + Z-Order
**Confidence:** HIGH (Stack + Patterns: HIGH; Open-Discretion Picker-Wahl: MEDIUM)
**Supabase Project:** vitrqkzxkiqvadqfzrcx (Frankfurt, EU)

## Executive Summary

Phase 09.1 erweitert den existierenden zweiplattformigen Editor (Web SVG `WebPlanEditor.tsx` + iPhone Skia `EditorCanvas.tsx`) um vollständige Element-Bearbeitung nach dem ersten Platzieren. **Keine neue Migration**, **keine neue Library für State/Gestures/Persistenz** — alles läuft auf bereits installiertem Stack: Skia 1.12.4, gesture-handler 2.31.2, zundo 2.3.0, Zustand 5.0.2, react-native-svg 15.15.4, react-native-reanimated 3.17.4.

**Was die Plans wissen müssen:**

- **Datenfluss steht.** `editorStore.updateElement(id, patch)` triggert zundo (1 Snapshot) + Auto-Save (5s debounce per Element) automatisch. Jede Bearbeitung — Resize/Rotate/Z-Order/Notiz — ruft genau diese Action. `setGestureActive(true)` während Drag-Handle-Bewegungen unterdrückt Autosave-Spam; `updateElement` final bei `onEnd` schreibt 1 Snapshot.
- **Render-Sortierung muss umgestellt werden.** Heute rendern beide Editoren in DB-Reihenfolge (`elements.map`). Wave 1 fügt `sortByZOrder(elements)` ein — ein reines Sort-Comparator-Modul auf `provenance.zOrder ?? 0`. Stable Sort + tie-break über `createdAt` ist Pflicht (sonst Flicker beim Re-Render).
- **Rotation muss visuell gerendert werden.** Heute steht `provenance.rotateDeg` in der DB, wird aber in keinem Renderer angewandt. SVG: `<G transform="rotate(deg, cx, cy)">`. Skia: `Group transform={[{rotate: rad}]}` mit Origin-Verschiebung (Skia rotiert um (0,0), daher translate-rotate-translate). Beide Editoren ändern sich in Wave 3.
- **Trigger-Disambiguierung ist Standard-Pattern.** Skia: `Gesture.LongPress().minDuration(500).maxDistance(10)` in `Gesture.Exclusive(longPress, tap)` und das gesamte Bündel in `Gesture.Race(twoFinger, pan, exclusive(longPress, tap))` — exakt das bestehende Composed-Layout in `EditorCanvas.tsx` Zeile 175 erweitert um `.onStart(handler)`. Web: nativer DOM-`onDoubleClick` auf `<G>` Element (react-native-svg auf Web rendert echte DOM-SVG-Elemente).
- **15°-Snap ist 3 Zeilen Math.** `Math.round(deg / 15) * 15` mit Shift-Override (Web: KeyboardEvent Capture). Skia hat kein Shift — daher kein Modifier-Override auf Mobile (Modal-Eingabe ist der freie Pfad).
- **Date-/Color-Picker:** `@react-native-community/datetimepicker@9.1.0` für Date (offizielle Expo-Empfehlung), `reanimated-color-picker@3.0.6` für Color (SDK 53-kompatibel — neuere Versionen erfordern Expo 56). Beide haben Web-Support. Im Web mit Fallback auf native `<input type="date">` und `<input type="color">` via Platform.OS-Switch — minimaler Code.
- **Modal-Pattern existiert bereits.** `BedPickerModal.tsx` ist die Referenz: `<Modal transparent animationType="fade" onRequestClose={onCancel}>` + `<Card>` + Footer mit `<Button>`. ESC/Hardware-Back werden automatisch via `onRequestClose` gehandhabt. Pending changes verwerfen — Undo fängt das ab (D-18).

**Primary recommendation:** 6 Plans im Wellen-Pattern aus Phase 7/6.5. Plan 1 (Wave-0 Test-Scaffold) + Plan 2 (Data/Store: sortByZOrder, Z-Order-Action) + Plan 3 (Modal-Shell + Trigger-Gesten) + Plan 4 (Resize/Rotation-Handles) + Plan 5 (Render-Sortierung + Rotation-Rendering beider Editoren) + Plan 6 (i18n + Verification). Jeder Plan hat klare TDD-RED → GREEN Phase.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Trigger-Geste:**
- **D-01:** Plattform-spezifische native Gesten: Web (SVG) Doppelklick = Modal; Mobile (Skia) Long-Press ~500ms ohne Bewegung = Modal.
- **D-02:** Drei klar getrennte Gesten auf Skia: `tap` = selektieren, `drag` = verschieben, `long-press` = Editor öffnen. Disambiguierung via `LongPress.minDuration(500) + maxDistance < 10px`.
- **D-03:** Kein zusätzlicher "Bearbeiten"-Button im Toolbar.

**Resize + Rotation:**
- **D-04:** Hybrid — Modal mit Zahlen-Inputs + Drag-Handles auf Canvas.
- **D-05:** Eck-Handles (4 Punkte) für Resize. Shift = proportional (Web), Modal-Checkbox = Maintain-Ratio (Mobile).
- **D-06:** Separater Rotations-Handle mittig über dem Element (16–24px Offset).
- **D-07:** Rotation-Snap 15°. Shift (Web) deaktiviert Snap. Modal-Eingabe: freie Grad.
- **D-08:** Skia 2-Finger-Rotations-Geste bleibt aktiv; Handle ist additiv.

**Eigenschaften im Modal:**
- **D-09:** Kern-Felder: Name, Breite × Höhe (cm), Rotation (Grad), Z-Order (4 Buttons).
- **D-10:** Erweiterte Felder: Notiz (`provenance.note`), Pflanzdatum (`provenance.plantedAt` ISO-Date), Akzentfarbe (`provenance.accentColor` hex).
- **D-11:** Erweiterte Felder default-collapsed, Counter "(3)" wenn gesetzt.

**Z-Order:**
- **D-12:** 4 Photoshop-Style Buttons: "Ganz nach vorne / Eine vor / Eine zurück / Ganz nach hinten".
- **D-13:** `provenance.zOrder: number` (Integer, default 0). Ascending Render-Sortierung.
- **D-14:** "Eine Ebene vor" = nächst-höhere Z im selben Beet finden, +1. Lazy, kein Renumbering.
- **D-15:** Z-Order ist plan-weit (nicht beet-lokal).

**Modal:**
- **D-16:** Follow `BedPickerModal.tsx` Pattern: RN `<Modal>` + `<Card>` + `<Button variant>`.
- **D-17:** Footer: "Abbrechen" (ghost) + "Speichern" (default) + "Löschen" (destructive).
- **D-18:** ESC (Web) + Hardware-Back (Android) schließen ohne Confirm — Undo fängt das ab.

**Datenmodell:**
- **D-19:** Keine neue DB-Migration. Alles in `plan_elements.provenance: jsonb`.
- **D-20:** `widthM`/`heightM` sind dedizierte Spalten — direkter Patch.
- **D-21:** `label` ebenfalls dedizierte Spalte.

**Undo/Redo:**
- **D-22:** Jede Bearbeitung ruft `updateElement()`. Eine Modal-Speicherung = 1 Snapshot. Drag-Ende = 1 Snapshot. Während Drag: `setGestureActive(true)`.

**i18n:**
- **D-23:** Keys unter `editor.elementEditor.*`.
- **D-24:** UTF-8 Umlaute strikt (siehe Memory `feedback_german_umlauts.md`).

### Pattern 1: Skia Long-Press Disambiguation (Focus 1)

**What:** Three discrete gestures on the canvas must not collide: `tap` (select), `pan` (drag-move), `longPress` (open editor).
**When to use:** Mobile Skia editor — any element-level interaction.
**Source:** Existing `EditorCanvas.tsx:175` already uses the exact composition; only the `.onStart()` on the longPress needs a real handler.

**Current code in `app/src/components/editor/EditorCanvas.tsx:146-179`:**
```typescript
const tap = Gesture.Tap().onEnd((e) => {
  runOnJS(handleCanvasTap)(e.x, e.y);
});
// Reserved for future context-menu (long-press on canvas, not on palette card).
const longPress = Gesture.LongPress().minDuration(500).onStart(() => {});

const rotation = Gesture.Rotation()...;
const twoFinger = Gesture.Simultaneous(pinch, rotation);
const composed = Gesture.Race(
  twoFinger,
  pan,
  Gesture.Exclusive(longPress, tap),
);
```

**Phase 09.1 extension:**
```typescript
// Phase 09.1: long-press opens element editor. Hit-test on UI thread first;
// if pointer is over an element (bounding-box test), capture its id, then runOnJS.
const longPress = Gesture.LongPress()
  .minDuration(500)
  .maxDistance(10)               // <-- D-02: cancel if finger moves >10px (drag intent)
  .onStart((e) => {
    'worklet';
    const vm = { tx: tx.value, ty: ty.value, scale: scale.value };
    // screenToGarden is already used in EditorCanvas; reuse it
    const xM = (e.x - vm.tx) / vm.scale;
    const yM = (e.y - vm.ty) / vm.scale;
    // Hit-test in worklet (no JS bridge)
    const elems = useEditorStore.getState().elements;  // ⚠ getState NOT useState in worklet
    const hit = elems.find(el => 
      el.deletedAt === null &&
      xM >= el.xM - el.widthM / 2 &&
      xM <= el.xM + el.widthM / 2 &&
      yM >= el.yM - el.heightM / 2 &&
      yM <= el.yM + el.heightM / 2
    );
    if (hit) runOnJS(openEditor)(hit.id);
  });
```

**Pitfall:** `Gesture.Exclusive(longPress, tap)` means once longPress fires, tap is cancelled and vice versa. This is exactly what we want — see existing composed gesture. **But `useEditorStore.getState()` inside a worklet is technically a JS-thread call from worklet boundary**. Safer: read elements via shared value or call `runOnJS(handleLongPressAt)(xM, yM)` with the coords and do the hit-test on JS-thread. Both work; the latter is simpler and consistent with `handleCanvasTap` on line 65.

**Source:** [VERIFIED: existing EditorCanvas.tsx:175 composed gesture pattern, Phase 7 P04]; [CITED: react-native-gesture-handler docs `LongPress.maxDistance`]

### Pattern 2: Web Double-Click on SVG Element (Focus 2)

**What:** Open ElementEditorModal when user double-clicks an SVG element in WebPlanEditor.
**When to use:** Web editor — Doppelklick = Modal (D-01).
**Source:** Existing `WebPlanEditor.tsx:296` uses `onMouseDown={handleElementMouseDown}` cast `as any` because react-native-svg's `<G>` type doesn't declare DOM events. **Same cast works for `onDoubleClick`**.

**Implementation (additive to existing `<G>` line 294):**
```typescript
<G
  key={el.id}
  onMouseDown={((e: React.MouseEvent) => handleElementMouseDown(el.id, e)) as any}
  onDoubleClick={((e: React.MouseEvent) => {
    e.stopPropagation();
    setEditingElementId(el.id);    // local state in WebEditorShell
  }) as any}
  style={{ cursor: 'grab' } as any}
>
```

**Verification:** react-native-svg on web renders **native DOM SVG elements** (react-native-svg-web exports SVG elements directly). [VERIFIED: WebPlanEditor.tsx already passes `onMouseDown` via cast and it works at runtime — production code since Phase 7.5a]. DOM SVG natively supports `dblclick`, which React surfaces as `onDoubleClick`.

**Drag-vs-Double-Click conflict:** `onMouseDown` fires before `onDoubleClick`. Two strategies:
1. Track time between mousedowns; if <300ms apart, suppress drag and trigger edit (manual debounce).
2. **Simpler:** Let drag fire normally — on mouseUp without movement, do nothing. The browser still resolves the dblclick on the 2nd mouseup. If the 1st click moved the element by a tiny pixel, the 2nd-click still detects and opens. Verify with manual test; in practice the user pauses imperceptibly between clicks.

### Pattern 3: Resize + Rotation Handles — Geometry (Focus 3)

**Single source of truth for bounds:** Element-local axis-aligned bounding box defined by `xM` (center), `yM` (center), `widthM`, `heightM`. **Rotation transforms the rendering, NOT the stored bounds.** Handles are drawn at the bounds' corners, then the entire element-plus-handles group rotates as one.

**Handle positions (in element-local meter space, before rotation):**

| Handle | Position (rel. to element center) |
|--------|-----------------------------------|
| top-left | `(-w/2, -h/2)` |
| top-right | `(+w/2, -h/2)` |
| bottom-left | `(-w/2, +h/2)` |
| bottom-right | `(+w/2, +h/2)` |
| rotation | `(0, -h/2 - HANDLE_OFFSET)` — above element center |

`HANDLE_OFFSET` ≈ `0.4 m` (matches ~20px at default 50px/m scale).

**Transform order (CRITICAL — wrong order produces wrong-axis resize):**

1. **Render order:** translate-to-center → rotate → draw-element-at-origin → draw-handles-at-origin-relative-positions.
2. **Resize math during drag:** Compute pointer position in **element-local unrotated space**:
   - `dx = pointerX_M - cx, dy = pointerY_M - cy` (vector from element center to pointer)
   - Inverse-rotate: `(dx', dy') = rotate(dx, dy, -rotateDeg)`
   - New width = `2 * |dx'|`, new height = `2 * |dy'|` (for corner-handle drag)
3. **Resize anchor:** Opposite corner stays fixed. This requires updating `xM`, `yM` as well as `widthM`, `heightM`. For an unrotated element dragging bottom-right corner: new w = pointerX - leftEdge; new h = pointerY - topEdge; new center = midpoint.

**Anti-pattern (DO NOT):** Compute new bounds in screen space then apply inverse-transform. Accumulates floating-point error and feels jittery.

**For MVP simplicity recommendation:**
- **Phase 09.1 v1:** Resize handles work only when `rotateDeg === 0`. If element is rotated, hide resize handles (show only rotation handle), force user to either reset rotation or use Modal for exact dimensions. This is the **explicit MVP carve-out** — Figma/Sketch implement rotated resize but it's a ~200-LOC math implementation.
- **Phase 09.1 v2 (deferred):** Implement rotated-resize math.

This carve-out is consistent with D-04 (Modal exists for precise values). **Recommend stating this explicitly in PLAN-checker assertions.**

**Source:** [ASSUMED — based on standard 2D editor conventions like Figma/Excalidraw]; [VERIFIED: existing rotation rendering plan from Phase 7 RESEARCH §Pattern 2 confirms rotation+resize complexity warrants MVP carve-out]

### Pattern 5: Z-Order Algorithm (Focus 5)

**Module:** `app/src/lib/editor/zOrder.ts` — 4 pure functions.

```typescript
import type { PlanElementRow } from '@spatenstich/shared';

function getZOrder(el: PlanElementRow): number {
  const prov = (el.provenance ?? {}) as Record<string, unknown>;
  return typeof prov.zOrder === 'number' ? prov.zOrder : 0;
}

/** "Eine Ebene vor" — find next-higher z (plan-wide per D-15), set this element to next-higher + 1. */
export function bringForward(elements: PlanElementRow[], targetId: string): number {
  const target = elements.find(e => e.id === targetId);
  if (!target) return 0;
  const targetZ = getZOrder(target);
  const higherZs = elements
    .filter(e => e.id !== targetId && e.deletedAt === null && getZOrder(e) > targetZ)
    .map(getZOrder);
  if (higherZs.length === 0) return targetZ;  // already on top, no-op
  const nextHigher = Math.min(...higherZs);
  return nextHigher + 1;
}

/** "Eine Ebene zurück" — find next-lower z, set this element to next-lower - 1. */
export function sendBackward(elements: PlanElementRow[], targetId: string): number {
  const target = elements.find(e => e.id === targetId);
  if (!target) return 0;
  const targetZ = getZOrder(target);
  const lowerZs = elements
    .filter(e => e.id !== targetId && e.deletedAt === null && getZOrder(e) < targetZ)
    .map(getZOrder);
  if (lowerZs.length === 0) return targetZ;  // already on bottom, no-op
  const nextLower = Math.max(...lowerZs);
  return nextLower - 1;
}

/** "Ganz nach vorne" — max(zOrder) + 1 over all non-deleted elements except self. */
export function bringToFront(elements: PlanElementRow[], targetId: string): number {
  const others = elements.filter(e => e.id !== targetId && e.deletedAt === null);
  if (others.length === 0) return 0;
  return Math.max(...others.map(getZOrder)) + 1;
}

/** "Ganz nach hinten" — min(zOrder) - 1. */
export function sendToBack(elements: PlanElementRow[], targetId: string): number {
  const others = elements.filter(e => e.id !== targetId && e.deletedAt === null);
  if (others.length === 0) return 0;
  return Math.min(...others.map(getZOrder)) - 1;
}

/** Stable sort comparator — ascending zOrder, tiebreaker createdAt for visual stability. */
export function sortByZOrder(elements: PlanElementRow[]): PlanElementRow[] {
  return [...elements].sort((a, b) => {
    const za = getZOrder(a);
    const zb = getZOrder(b);
    if (za !== zb) return za - zb;
    // Tiebreaker: createdAt ascending so newer elements render on top within same z-band
    return a.createdAt.localeCompare(b.createdAt);
  });
}
```

**Caller pattern in modal:**
```typescript
const onBringForward = () => {
  const newZ = bringForward(elements, editingElementId);
  const prev = (currentEl.provenance ?? {}) as Record<string, unknown>;
  updateElement(editingElementId, { provenance: { ...prev, zOrder: newZ } });
};
```

**Negative zOrder is allowed** (sendBackward from 0 produces -1). Both signed integers are well-supported in jsonb. No renumbering ever — IDs drift but order is preserved.

### Pattern 7: Live Preview Without Snapshot Spam (Focus 7)

**Existing pattern in `editorStore.ts:31-32`:**
```typescript

```

**Existing usage in `editorStore.ts:174-184` (the auto-save subscription):**
```typescript

  if (state.gestureActive) return;        // <-- skip during drag
  if (state.elements === prev.elements) return;
```

**KEY INSIGHT:** The autosave subscription skips during gestureActive, but **zundo still captures snapshots on every updateElement call**, because zundo wraps the setter, not the subscription. So calling `updateElement` 60x/second during a drag creates 60 history entries.

**Two fixes to consider:**

**Option A (recommended):** Direct shared-value rendering during drag, single `updateElement` on `onEnd`.

```typescript
// During drag — write to a Reanimated SharedValue for canvas rendering only
const dragWidthM = useSharedValue<number | null>(null);
// In the resize handle gesture:
.onChange((e) => {
  'worklet';
  const newWidth = computeNewWidth(e);
  dragWidthM.value = newWidth;   // canvas reads this SharedValue while dragging
})
.onEnd(() => {
  'worklet';
  const final = dragWidthM.value;
  if (final !== null) {
    runOnJS(commitResize)(editingId, final);  // ONE updateElement call, ONE snapshot
    dragWidthM.value = null;
  }
});
```

**Option B:** Suppress zundo during gestureActive. Wrap the setter:
```typescript
// In editorStore.ts, before temporal middleware:
const tempApi = useEditorStore.temporal;
const origPause = tempApi.getState().pause;
const origResume = tempApi.getState().resume;
useEditorStore.subscribe((s, prev) => {
  if (s.gestureActive && !prev.gestureActive) tempApi.getState().pause();
  else if (!s.gestureActive && prev.gestureActive) tempApi.getState().resume();
});
```

zundo's `pause()` and `resume()` are first-class APIs. [CITED: github.com/charkour/zundo README]. This is the standard solution.

**Recommendation:** **Option B is simpler and works without SharedValue plumbing.** Use it for resize/rotation drags. Web (mousemove) sets gestureActive in the existing mousedown handler (already done at line 205 of WebPlanEditor.tsx); Skia sets it via `setGestureActive(true)` on `.onBegin()` (already done at line 88-94 of EditorCanvas.tsx).

**The full integration:**
- During handle drag: store is paused (zundo doesn't capture); autosave subscription skips. UI re-renders normally per updateElement call.
- On drag end: setGestureActive(false) → autosave fires once, zundo resumes (next updateElement creates one snapshot).
- **However** there's a subtle issue: the **final updateElement** call between pause-and-resume may not be captured. The flow needs to be:
  1. `setGestureActive(false)` (resumes zundo)
  2. ONE final `updateElement(id, {finalWidth, finalHeight})` — this captures the snapshot

Or simpler:
- During drag, suppress zundo via pause().
- On drag end, **call updateElement once** with the final value. This creates the single snapshot.
- Then setGestureActive(false) (autosave runs).

### Anti-Patterns to Avoid

- **DO NOT** read editorStore via React selector inside a Skia worklet — use `useEditorStore.getState()` outside the worklet, pass values in via Reanimated SharedValues, or `runOnJS` callbacks.
- **DO NOT** store Modal form state in editorStore. Form state is local React state in `ElementEditorModal.tsx`; only on Save does it flow to the store.
- **DO NOT** add a new column for zOrder. Use `provenance.zOrder` — keeps Migration count at 019, honors D-19.
- **DO NOT** apply rotation to the rendered children individually. Apply ONE transform on a parent Group (SVG `<G transform="rotate(deg, cx, cy)">` or Skia `<Group transform=[...]>`). Children are rendered in element-local space.
- **DO NOT** mutate `provenance` in place. Always `provenance: { ...prev, zOrder: newZ }` — partial overwrites destroy other fields (rotateDeg, plantSlug, source).
- **DO NOT** snap rotation in Modal numeric input. Modal = freie Rotation per D-07.
- **DO NOT** use `<DateTimePicker>` directly in shared component files — lazy-require it inside Platform.OS branch (otherwise Metro web bundle breaks).

## Common Pitfalls

### Pitfall 1: Skia Long-Press fires on canvas-only-pan (no element underneath)

**What goes wrong:** User long-presses on empty canvas; ElementEditorModal opens with `null` element → crash or empty modal.
**Why it happens:** Long-press fires on the canvas root, not on individual elements. Skia has no DOM-tree event-bubbling.
**How to avoid:** Inside the longPress handler, run the hit-test (same as Tap at `EditorCanvas.tsx:65-85`). If no element hit, ignore.
**Warning signs:** Empty modal renders, `editingElementId` is set but element lookup returns undefined.

### Pitfall 2: Web onDoubleClick swallowed by drag detection

**What goes wrong:** User double-clicks on element, drag starts on 1st click and snaps element by 1px before 2nd click fires; double-click event suppressed because mouse "moved".
**Why it happens:** Browser dblclick requires both clicks to be on the same element without movement between them.
**How to avoid:** Set drag-start threshold (5–8 pixels) before initiating drag. The current `handleElementMouseDown` (line 199) starts drag immediately — add a movement threshold or use mousemove with a small dead-zone.
**Warning signs:** Double-clicks intermittently don't open modal; works on careful slow double-click but not fast double-click.

### Pitfall 3: zOrder runaway after many bringToFront calls

**What goes wrong:** User clicks "Ganz nach vorne" 50 times on the same element; zOrder becomes 50, 51, 52, … Eventually accumulates pollution.
**Why it happens:** Lazy algorithm always adds 1 to max; never normalizes.
**How to avoid:** Acceptable for MVP — integers in jsonb have no practical ceiling. If desired, add an opportunistic renumbering on app load: when loading elements, if max(zOrder) > elements.length * 100, run a pass that sorts elements and reassigns sequential zOrders. Defer to Phase 14 polish.
**Warning signs:** Strange large numbers in DB inspection (not a functional bug).

### Pitfall 4: Resize handle position off after rotation

**What goes wrong:** Element is rotated 45°; resize handles still draw at unrotated corners. Drag-to-resize math computes wrong delta.
**Why it happens:** Handles rendered in screen-space, not rotated with element.
**How to avoid:** Render handles **inside** the rotated Group (SVG `<g transform="rotate(...)">`) — they rotate as part of the element. Math during drag must inverse-rotate the pointer vector before applying as width/height (see Pattern 3).
**Warning signs:** Rotated element shrinks wrongly when corner dragged; handles appear in wrong direction.
**MVP carve-out:** Hide resize handles when rotated (only show rotation handle); user can still resize via Modal numeric input.

### Pitfall 5: provenance overwrite destroys plantSlug

**What goes wrong:** User edits a plant element's accent color; `updateElement(id, { provenance: { accentColor: '#FFAA00' } })` overwrites the entire jsonb, deleting `plantSlug` which Phase 9 companion detection relies on.
**Why it happens:** Shallow merge by updateElement (`{ ...e, ...patch }`) but `patch.provenance` itself is not deep-merged.
**How to avoid:** ALWAYS spread previous provenance when patching:
```typescript
const prev = (currentEl.provenance ?? {}) as Record<string, unknown>;
updateElement(id, { provenance: { ...prev, accentColor: newColor } });
```
**Warning signs:** Companion detection stops working after editing a plant's accent color; conflicts disappear from previously-conflicting elements.
**Mitigation:** Provide an `updateElementProvenance(id, partialProv)` action in editorStore that always deep-merges. Add unit test.

### Pitfall 6: Modal renders behind other Modals (companion toast)

**What goes wrong:** ElementEditorModal opens; CompanionToast (also a Modal-like overlay) renders above it, blocking interaction.
**Why it happens:** RN Modal z-index isn't deterministic; depends on mount order.
**How to avoid:** CompanionToast in `plan/index.tsx:226-233` is NOT a real Modal — it's a `<View pointerEvents="box-none">` overlay. Should not collide. Verify on Web (DOM stacking context).
**Warning signs:** Toast appears above modal in screenshots.

### Pitfall 7: Web shift-key event lost while modal input is focused

**What goes wrong:** User opens modal, types in name input, then switches to canvas rotation handle while holding shift. KeyboardEvent listener was bound globally and is still listening, but TextInput focus consumed shift.
**Why it happens:** Window-level keydown listeners receive shift even when input is focused, IF the listener doesn't check `e.target`.
**How to avoid:** Use `e.target?.tagName` check (existing pattern in WebPlanEditor.tsx:101-103). Listener should ignore events when an INPUT/TEXTAREA is focused.
**Warning signs:** Snap doesn't disable on shift when modal is also visible.

### Pitfall 8: zundo pause not resumed after error during drag

**What goes wrong:** Skia gesture handler throws mid-drag (e.g., element deleted by sync from other user); `setGestureActive(false)` never called → zundo stays paused forever, undo stops working.
**Why it happens:** No try/finally on gesture handler.
**How to avoid:** Wrap onChange logic in try/catch, ensure setGestureActive(false) in cleanup. Add a defensive timeout in editorStore: if gestureActive=true for >10s, force-reset.
**Warning signs:** Undo button greyed out permanently after a drag interaction.

## Open Questions (RESOLVED)

1. **Rotated resize math complexity vs MVP timeline**
   - What we know: Phase 7 P04 implemented rotation as 2-finger gesture but never tested combined rotation+resize edge cases. Figma-grade rotated-resize math is ~200 LOC.
   - What's unclear: Whether to ship MVP with "resize disabled when rotated, only rotation handle visible" or invest in full math.
   - **Recommendation:** MVP carve-out — hide resize handles when `rotateDeg !== 0`. User can resize via Modal numeric inputs. Document in PLAN as explicit constraint. Defer full rotated-resize to Phase 14.

2. **Web double-click vs drag conflict tolerance**
   - What we know: `handleElementMouseDown` (WebPlanEditor.tsx:199) immediately initiates drag on mousedown.
   - What's unclear: How often will users click twice with imperceptible movement? Need manual test.
   - **Recommendation:** Implement movement threshold (5px) before drag commits — i.e., delay setting `drag` state until mousemove exceeds threshold. This naturally permits clean double-clicks. Add as a refinement in Plan 3.

3. **Mobile Shift-key equivalent for free rotation**
   - What we know: D-07 says "Shift (Web) deaktiviert Snap." No equivalent specified for Mobile.
   - **Recommendation:** Mobile always snaps via handle. For free rotation on mobile, use Modal numeric input. Document as Mobile-Web asymmetry in CONTEXT D-07 clarification — confirm with user before Plan 4.

4. **Color contrast / accessibility for accent color**
   - What we know: Default Beet color is `PLAN_COLORS.Beet` (a stone-ish tone). If user picks `#FFFFFF` accent, label text may become invisible.
   - **Recommendation:** Compute contrast ratio at render time; if below 4.5:1, render text in `darkenColor(accent, 0.6)`. Use existing `darkenColor` helper. Defer if scope blows out; document as known limitation.

5. **Should "Pflanzdatum" auto-set on placement for new plants?**
   - What we know: D-10 says it's an optional field. Today new plants have no plantedAt.
   - **Recommendation:** Leave default null. Phase 10 (Aussaatkalender) reads the field; if null, it falls back to estimated date. Surface as a sentence in deferred-ideas.
