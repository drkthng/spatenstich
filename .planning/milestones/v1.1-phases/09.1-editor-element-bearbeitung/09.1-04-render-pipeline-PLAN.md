<objective>
Render-Pipeline beider Editor-Implementationen (Skia + Web-SVG) auf zOrder-sortierte
Ausgabe + per-Element Rotation-Transform umstellen. Setzt D-13 (`provenance.zOrder` als
Render-Sort-Key, ascending), D-14 (lazy non-renumbering Konflikt-Strategie sichtbar),
D-15 (plan-weite Reihenfolge) und D-20 (`widthM`/`heightM` als dedizierte Spalten, nicht
provenance) auf der Render-Schicht um. Zusätzlich: optionaler `provenance.accentColor`-
Override schlägt default `PLAN_COLORS[elementType]` aus.

Purpose: Ohne diesen Plan haben die Z-Order-Buttons aus Plan 02 (D-12) keinen sichtbaren
Effekt — sie schreiben `provenance.zOrder`, aber beide Renderer ignorieren das Feld. Ohne
den Rotation-Transform würde die Rotation aus Plan 03 (Drag-Handle) zwar im Store landen,
aber das Element bleibt visuell achsenparallel. Plan 04 schließt die Wahrnehmungslücke
zwischen Store-State und Pixel-Output.

Output: Beide Renderer iterieren `sortByZOrder(elements)` statt der rohen Array-Reihenfolge
und wickeln jedes Element in eine Rotation-Transformation um seinen Mittelpunkt — Skia via
`<Group transform={[...]}>` mit 5-Matrix-Stack (translate→rotate→un-translate), Web-SVG via
`transform="rotate(${deg}, ${cxPx}, ${cyPx})"`. Beide Tests aus Wave 0 (`EditorCanvas.rotation.test.tsx`,
`WebPlanEditor.rotation.test.tsx`) werden GREEN.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| store→renderer | `provenance.zOrder` und `provenance.rotateDeg` sind untrusted Eingabewerte aus jsonb — können beliebige numerische Werte enthalten (negativ, NaN, Infinity, Non-Number) |
| store→renderer (accentColor) | `provenance.accentColor` ist user-getippter Hex-String — kann ungültig sein (von alten Builds, manuellen DB-Edits, fehlerhaftem Import) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09.1-RENDER-ORDER | Tampering | sortByZOrder Konsumenten (EditorCanvas + WebPlanEditor) | mitigate | `sortByZOrder` aus Plan 01 hat deterministischen createdAt-Tiebreaker — Plan 04 muss garantieren, dass das Array NICHT in-place sortiert wird (sortByZOrder gibt neues Array zurück, siehe Plan 01 Implementation). EditorCanvas + WebPlanEditor rufen sortByZOrder VOR jedem `.map` auf und mutieren keine Render-Daten. |
| T-09.1-NAN-ROTATION | Tampering | Rotation-Transform | mitigate | Beide Renderer lesen `rotateDeg` mit `typeof prov.rotateDeg === 'number' ? prov.rotateDeg : 0` (Pattern aus PATTERNS.md §EditorCanvas.tsx Phase 09.1 extend). NaN ist `typeof 'number'`, also wird hier `Number.isFinite()` zusätzlich geprüft, Fallback `0`. |
| T-09.1-XSS-ACCENT-COLOR | Injection | accentColor override (Web SVG fill attribute) | mitigate | Wenn `provenance.accentColor` als Fill ins SVG fließt, muss er die Hex-Regex `/^#[0-9a-fA-F]{6}$/` aus Plan 02 (CrossPlatformColorPicker) passieren. Plan 04 validiert beim Lesen: `const fill = isValidHex(accent) ? accent : defaultFill;`. Verhindert SVG-Attribute-Injection (z.B. `red;onload=alert(1)`). |
| T-09.1-RENDER-PERF | Denial of Service | sortByZOrder Aufruf pro Render | accept | `sortByZOrder` ist O(n log n). Bei 50 Elementen (Stack-Constraint) ist das << 1ms. Akzeptabel — kein Memoization-Layer in MVP. Bei > 50 Elementen ist die Skia-Upgrade-Schwelle (Stack-Constraint) sowieso bereits überschritten. |
| T-09.1-Z-INTEGRITY | Tampering | sortByZOrder consumer | transfer | Algorithmus-Garantien (idempotent, stabil, createdAt-Tiebreaker) sind in Plan 01 abgedeckt. Plan 04 nutzt nur die geprüfte API. |
</threat_model>
