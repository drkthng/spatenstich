# Phase 06.5: Code Review Report

**Reviewed:** 2026-05-12T00:00:00Z
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

Phase 06.5 introduces the Sichtungs-Screen at `/(app)/import/review`, the `draftPromotionRepo` (5 exports), migration 017 with `imported_from` + `provenance` provenance columns on `plan_elements`, and rewires `preview.tsx` to redirect to review. Architecture, schema, and i18n discipline are solid; tests cover the documented critical paths (Crit-1 through Crit-7 plus Pitfall-1..3).

Two correctness defects stand out:

1. **CR-01 (parent-bed link is permanently broken):** plant→bed parent lookup compares `bed_drafts.id` against `plan_elements.imported_from` (which carries `import_items.id`). These are different UUID spaces, so `parent` is always `null`. The DRAFT-02 acceptance criterion "plants link to parent bed via provenance.parentBedId" is silently failing for every plant that has a `bedDraftId`. The test fixtures all set `bedDraftId: null`, so the bug is invisible to the current test suite.

2. **CR-02 (`randomId()` can emit non-UUID strings):** the fallback path returns `${Date.now()}-${Math.random()...}` which is not a UUID. `plan_elements.id` and `plan_elements.imported_from` are typed `uuid` in Postgres (migration 014/017). On Hermes / older WebViews where `crypto.randomUUID` is unavailable, every promoted element will fail the sync push with a uuid-format error and queue indefinitely in the outbox.

Warnings cluster around the auto-promote batch: stale `elements` state between iterations breaks idempotency and parent-linking inside one batch, and a single failure aborts the rest of the batch. Quality issues are minor (typed routes via `as any`, store doc-comment vs runtime behaviour).

## Critical Issues

### CR-01: Plant→bed parent lookup compares wrong ID spaces — always returns null

**File:** `app/app/(app)/import/review.tsx:96` and `app/app/(app)/import/review.tsx:163-165`
**Issue:**
Both `handleAcceptPlant` and `triggerAutoPromote` look up the parent bed element via:

```ts
elements.find((e) => e.importedFrom === draft.bedDraftId && e.deletedAt === null)
```

But:
- `PlantDraftRow.bedDraftId` references `bed_drafts.id` (the local draft row UUID).
- `PlanElementRow.importedFrom` is set in `promoteBedDraft` to `importItemId`, i.e. `import_items.id`.

These are two different UUID spaces. The lookup can therefore never match, and `parentBedElement` is always `null` for every plant that has a `bedDraftId`. As a result `provenance.parentBedId` is always `null` and the plant is placed at `(0, 0)` instead of next to the parent bed (`parentBedElement.xM + 0.2`, etc.).

The unit tests pass because `ImportReview.test.tsx`/`autopromote.test.tsx` set `bedDraftId: null` on every plant fixture, and `draftPromotionRepo.test.ts` injects `parentBedElement` directly. No test exercises the screen-level lookup.

**Fix:**
Resolve the parent via the bed-draft's `importItemId` (or carry `bed_drafts.id` through to `plan_elements.provenance.bedDraftId` during bed promotion and match on that). Minimal patch:

```ts
// review.tsx — both call-sites
const parentBedDraft = draft.bedDraftId
  ? drafts.beds.find((b) => b.id === draft.bedDraftId) ?? null
  : null;
const parent = parentBedDraft
  ? elements.find(
      (e) => e.importedFrom === parentBedDraft.importItemId && e.deletedAt === null,
    ) ?? null
  : null;
await promotePlantDraft(mode, draft, parent, draft.importItemId);
```

Add a regression test with a non-null `bedDraftId` and a matching promoted bed element to lock the behaviour.

### CR-02: `randomId()` fallback emits non-UUID values, breaking sync on Hermes

**File:** `app/src/lib/draftPromotionRepo.ts:23-28`
**Issue:**

```ts
function randomId(): string {
  if (typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function') {
    return crypto.randomUUID();
  }
  return `${Date.now()}-${Math.random().toString(36).slice(2, 10)}`;
}
```

The fallback string (e.g. `1715472000000-a8b3kz9q`) is not a valid UUID. It is written to `plan_elements.id` (typed `uuid NOT NULL`) and consumed as `outbox.rowId`. On the Supabase push path, PostgREST will reject the insert with a uuid format error and the outbox entry will retry indefinitely.

Hermes (default RN runtime in Expo SDK 55) historically does not ship `crypto.randomUUID` — confirm before relying on it. The Web export's behaviour depends on the browser.

This is the only ID generator in the new repo, so every Beet/Pflanze created via the Sichtungs-Screen on a non-supporting runtime will silently fail to sync, while the local row appears fine. Combined with offline-first UX, the user will not notice until they reopen on another device.

**Fix:**
Use `expo-crypto`'s `randomUUID()` (already a transitive dep of `@supabase/supabase-js`) or `react-native-uuid`. Match the convention used by `importRepo.ts` / `gardenPlanRepo.ts` for IDs:

```ts
import * as Crypto from 'expo-crypto';

function randomId(): string {
  return Crypto.randomUUID();
}
```

If a shared id-helper exists elsewhere in the codebase, reuse it rather than re-implementing.

## Warnings

### WR-01: Stale `elements` state breaks idempotency + parent-link inside a single batch

**File:** `app/app/(app)/import/review.tsx:152-180` (`triggerAutoPromote`)
**Issue:**
`triggerAutoPromote` iterates over `drafts.beds`, `drafts.plants`, `drafts.observations` and calls the per-draft promote functions in series. Each call reads `elements` (captured by the `useCallback` closure) without re-reading from storage. Consequences:

1. The idempotency check inside `promoteBedDraft` (`existingElements.find(e => e.importedFrom === importItemId && deletedAt === null)`) never sees beds that were inserted earlier in the same batch — re-running auto-promote after a partial success could create duplicates if the upstream `bed_drafts.status` flag hasn't flipped to `'promoted'` yet (it has, via the second write, so this specific case is OK, but it's defensive-in-depth at risk).
2. Plant parent-lookup happens against pre-batch `elements`, so a plant whose parent bed is being promoted in the *same* batch can never find its parent — even if CR-01 is fixed.

`refresh()` only runs once at the end of the batch.

**Fix:**
Either:
- Re-read `dimensions` + `elements` from storage at the top of `triggerAutoPromote` and pass the freshly-promoted bed element back into the next iteration manually, or
- Track newly-created elements in a local array inside the loop and merge with `elements` for the plant pass.

Sketch:

```ts
const accumulated: PlanElementRow[] = [...elements];
for (const bed of drafts.beds) {
  if ((bed.confidence ?? 0) < threshold) continue;
  const el = await promoteBedDraft(mode, bed, dimensions, accumulated, bed.importItemId);
  accumulated.push(el);
}
for (const plant of drafts.plants) {
  // ... use accumulated for parent lookup
}
```

### WR-02: First failure aborts the rest of an auto-promote batch silently

**File:** `app/app/(app)/import/review.tsx:152-180`
**Issue:**
The whole batch is inside a single `try { for ... for ... for ... } catch { setPromoteError(...) }`. The first thrown promotion (e.g. a transient outbox enqueue error on draft #2 of 10) aborts the remaining drafts. The error banner shows, but the user has no signal that 8 of 10 high-confidence drafts were skipped — toggling auto-promote off and on again would partially re-run, but state is opaque.

**Fix:**
Move the try/catch inside each iteration, collect failures into an array, and surface a count: e.g. "Übernahme von 2 von 10 Drafts fehlgeschlagen". Continue processing remaining drafts on failure.

```ts
const failures: string[] = [];
for (const bed of drafts.beds) {
  if ((bed.confidence ?? 0) < threshold) continue;
  try { await promoteBedDraft(...); } catch (e) { failures.push(bed.id); }
}
// ... aggregate + surface failures
```

### WR-03: `nextFreeBedSlot` advances cursor without verifying overlap against the bed at each step

**File:** `app/src/lib/draftPromotionRepo.ts:42-64`
**Issue:**
The pure layout helper advances a horizontal cursor for each existing bed but does not actually check whether the candidate slot overlaps with the bed it iterates over. It works for the test fixtures (`bedAt('e1', 1, 1, 2, 1)`, `bedAt('e2', 3.5, 1, 2, 1)`) because the existing beds are pre-arranged left-to-right starting near (1, 1), matching the cursor's own advance pattern. For manually-placed beds at arbitrary positions (`bedAt(8, 6, ...)`), or any non-greedy layout, the helper can return slots that visually overlap with existing beds.

This is acceptable for MVP given that all current beds in scope come from the same auto-layout pass, but the helper's name and signature imply general-purpose collision avoidance.

**Fix:**
Either:
- Rename to `nextStackSlot` and document the assumption ("existing beds must be sorted by x, only call after a full layout reset"), or
- Replace with a real AABB-overlap scan over `beds` (still cheap at MVP scale ≤50 elements).

A real-overlap version (~10 lines, O(n) per call):

```ts
function overlaps(a, b) {
  return a.xM < b.xM + b.widthM && a.xM + a.widthM > b.xM &&
         a.yM < b.yM + b.heightM && a.yM + a.heightM > b.yM;
}
// scan candidate positions on a grid until first non-overlapping slot found.
```

### WR-04: `promotePlantDraft` skips idempotency check entirely

**File:** `app/src/lib/draftPromotionRepo.ts:166-238`
**Issue:**
Comment line 163-165: *"Idempotency check is left to the caller (UI re-loads pending drafts after each promote, so the screen never re-promotes a draft whose status flipped to 'promoted')."*

The single-action path works because `handleAcceptPlant` awaits `refresh()` before the user can click again. The auto-promote batch, however, does NOT refresh between iterations (see WR-01), and if the same plant draft were ever passed twice (e.g. duplicate import items, or a re-toggle of auto-promote racing with `bed_drafts.status` flip propagation), two plan_elements would be inserted.

The same risk applies to `promoteObservationDraft` (no idempotency at all) — though that only duplicates the `observation_drafts` update, which is harmless because of LWW.

**Fix:**
Mirror the `promoteBedDraft` idempotency check in `promotePlantDraft`: accept an `existingElements: PlanElementRow[]` arg and short-circuit when `e.importedFrom === importItemId && deletedAt === null` is found. Add a regression test analogous to `draftPromotionRepo.idempotency.test.ts`.

### WR-05: Edit-then-promote loses original lengthCm/widthCm when user clears the bed-dimension input

**File:** `app/app/(app)/import/review.tsx:128-150` (`handleEditSave`)
**Issue:**
When the bed edit form is saved with empty length/width inputs, `values.lengthCm` and `values.widthCm` are `null`. The merged draft sets `lengthCm = null`, `widthCm = null`. `promoteBedDraft` then falls back to the **defaults** (`(draft.lengthCm ?? 150)`), discarding whatever the import originally measured (e.g. 200×100). The user did not necessarily intend to reset to defaults — they may have just opened the form, edited the label, and pressed Save without re-entering numbers.

The form's `useState` initializes inputs from `initialValues.lengthCm/widthCm`, so if the user does not edit them they stay populated and survive. The bug only manifests when a user explicitly clears the field — debatable intent. Still worth flagging because the loss is silent.

**Fix:**
In `handleEditSave`, treat `null` returned from the form as "keep current value" rather than "reset":

```ts
if (kind === 'bed') {
  merged.lengthCm = values.lengthCm ?? draft.lengthCm;
  merged.widthCm = values.widthCm ?? draft.widthCm;
}
```

Alternatively, make the form distinguish "empty" from "unchanged" via a sentinel, or block save when the user clears a previously-populated field.

### IN-01: `reviewSettingsStore` comment claims "re-opens default to false" but state survives across mounts

**File:** `app/src/stores/reviewSettingsStore.ts:2-3`
**Issue:**
Comment: *"Session-scoped store for review screen auto-promote toggle. Not persisted — re-opens default to autoPromote=false."*

Zustand `create()` without `persist` middleware still keeps state for the lifetime of the JS runtime. Re-opening the review screen within the same session preserves `autoPromote`. Only a full app reload (process restart, web hard-refresh) resets it.

**Fix:** Either update the comment to "re-mounts within a session preserve the value; a full app reload resets to false" or reset on unmount in the screen if the intent really is per-screen-open default.

await storage.writeWithOutbox<AnyRow>(entity as EntityName, updated as unknown as AnyRow, {

Two `as unknown as` and one `as EntityName` cast hide the fact that the row union type does NOT include the draft tables narrowed on `entity`. Functionally correct because the underlying storage layer is duck-typed, but a typo in the `entity` string would not be caught.

### IN-05: `useEffect` dependency-loop guard in preview.tsx mirrors the test setup, but the production store may still return fresh references

**File:** `app/app/(app)/import/preview.tsx:33-45`
**Issue:**
The test file `preview-navigation.test.tsx:24-38` explicitly notes "returning a fresh object on every selector call makes useEffect([payload]) loop and triggers React's Maximum update depth guard." The production `useImportStore` selector here is `useImportStore((s) => s.payload)` which is fine **only as long as** the store does not re-create `payload` on every set. Worth a sanity check that no store action calls `set({ payload: { ...current } })` somewhere that would invalidate the reference.

**Fix:** None required — flagging for awareness. Consider adding `shallow` equality or a `useMemo` if any new store action mutates payload.

### IN-06: Migration 017 — `ON DELETE SET NULL` on `imported_from` silently loses provenance link

**File:** `supabase/migrations/20260512000017_plan_elements_provenance.sql:12`
**Issue:**
`imported_from uuid REFERENCES public.import_items(id) ON DELETE SET NULL` means: if an `import_items` row is ever deleted, the plan_element keeps existing but loses its provenance back-link. The `provenance` jsonb is not auto-cleared. For audit/forensic purposes this is fine, but for "re-promote idempotency check" (`existingElements.find(e => e.importedFrom === importItemId)`), nullification would cause a re-import of the same item to create a duplicate plan_element rather than de-dup against the previous one.

`import_items` are documented as write-once (`importEntityToDb` strips `updated_at`), so deletion is unusual but the soft-delete path in `dismissDraft` does NOT affect `import_items` (only the draft rows). So in practice this is dormant. Worth a comment in the migration.

**Fix:** Add a SQL comment explaining the trade-off:

```sql
-- imported_from: SET NULL on import_items delete is intentional —
-- plan_element survives but loses provenance link. Re-import after
-- import_items delete will create a duplicate plan_element (no
-- idempotency for orphaned elements).
```
